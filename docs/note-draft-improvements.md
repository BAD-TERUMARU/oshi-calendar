# 推し活カレンダーを「使える形」に。Codexで作って、実際に使って直したこと

前回、OCHA NORMA、モーニング娘。'26、宮本佳林の予定をひとつの画面で見られるカレンダーを作りました。

前回の記事「推し活の予定をひとつに。3組のライブ・イベントカレンダーをCodexで作った」：<https://note.com/badterumaru/n/n1c18a5acf355>

その時点では、まず予定を集めて眺められることを優先した試作版でした。実際に使ってみると、次のような改善点が見えてきました。

- スマートフォンでは、イベント名より先に「どこの現場か」が分かった方がよい
- ライブ、リリースイベント、ステージなどを分けて見たい
- 昼公演と夜公演を別々に「行きたい」として管理したい
- 予定を自分のカレンダーに登録したい
- チケット情報は、登録した時点と現在で変わる
- どの情報を公開してよいか、毎回判断が必要になる

今回は、これらを反映して、予定を見るだけのカレンダーから「どの現場に行くかを考え、公式情報へ戻るための作戦盤」に近づけました。

実装そのものだけでなく、使い続けるには「チケット情報をどう更新するか」「どこまで自動化するか」「何を公開情報として扱うか」といった問題も出てきました。今回は、そのあたりも含めた改善記録です。

実際のアプリはこちらです：<https://oshi-calendar.badterumaru.workers.dev/>

※本アプリは非公式のファン作成アプリです。掲載情報は2026年9月9日時点のスナップショットであり、最新情報や申込条件は必ず公式サイトで確認してください。

## 前回から、何が変わったか

一番大きく変わったのは、カレンダーを「予定の一覧」だけで終わらせず、現場へ行くための判断に使えるようにしたことです。

現在は、2026年9月9日時点で確認した公開情報をもとに、58件のイベントを登録しています。前回の記事を書いた2026年8月22日時点の40件から、告知されたイベントを追加し、受付状況や確認日も更新しました。

## 1. カレンダーを見た瞬間に、現場をイメージできるようにした

カレンダーでは、正式名称をそのまま表示すると、文字が長くなりがちです。そこで、カレンダー内では「秋ツアー福岡」「リミスタ（サイン会）」「北原ももBD」のように、何の予定か分かる短い名前を表示しています。

さらに、スマートフォンでは会場名をすべて表示するよりも、まず「東京」「大阪」「福岡」といった地名が見えた方が、遠征や移動を考えやすいと判断しました。画面の幅に応じて、カレンダー上は開催地を優先して表示します。

カレンダー自体も、日曜始まりから月曜始まりに変更しました。平日の予定と週末の現場を、普段のスケジュールに近い並びで確認できます。

日曜・祝日は赤字、土曜は青字にしています。祝日は内閣府の「[国民の祝日について](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)」をもとに、2026年と2027年分を同梱しました。

## 2. イベント種別で絞り込めるようにした

予定を全部表示すると、ライブを探したいときにリリースイベントやオンラインイベントも目に入ります。

そこで、登録内容に応じて、次のような種別で絞り込めるようにしました。

- ライブ
- フェス
- ステージ
- オンライン
- BDイベント
- 個別イベント
- リリースイベント

イベントデータの種別にはFCイベントやその他も含め、データに存在する種別だけを画面に表示する構造です。

すべて選択されている状態で「ライブ」を押すと、ライブだけが表示されます。最初から一つずつ解除するより、「いま見たいものだけを残す」操作の方が自然だと考えました。

## 3. 「行きたい」を、公演単位で管理できるようにした

気になるイベントを見つけたら、詳細画面で「行きたい」を選べます。

昼夜公演のように複数の公演がある場合は、イベント全体ではなく、1部・2部を公演単位で選択できます。開場・開演時刻も公演ごとに表示されます。

複数日にわたるイベントも、開催期間を丸ごと選ぶのではなく、自分が参加したい日付を個別に選ぶ形にしました。期間中の全日程へ自動的に予定を作らないため、実際の参加日とカレンダーの予定がずれにくくなります。

選んだ予定は、iCalendar形式の`.ics`ファイルとして書き出せます。開始時刻が公式に確認できた公演は時刻付きで、終了時刻が確認できない場合は開始時刻のみで出力します。自分用の終了予定を入力することもできますが、公式の終演時刻とは明確に区別しています。

## 4. カレンダーへの重複登録を減らす仕組みを入れた

一度選んだ予定を、もう一度書き出すたびに同じ予定が増えるのは困ります。

そこで、イベントIDと公演IDを組み合わせて、同じ公演を同じ予定として管理しています。出力履歴をブラウザに保存し、通常の「新規分をICS出力」では、まだ出力していない選択だけを対象にします。

ただし、`.ics`ファイルを取り込んだ後の重複判定は、Googleカレンダーやスマートフォンのカレンダーアプリ側の仕様にも左右されます。アプリ側で重複を減らす工夫はしていますが、外部カレンダーへの再取り込みまで完全に保証するものではありません。

「行きたい」の選択をすべて解除する機能と、出力履歴を消す機能も分けました。選択を解除しても、外部カレンダーに登録済みの予定は削除されません。

## 5. チケット情報は「確認日時点の記録」として扱う

今回の改善で、データの持ち方も見直しました。

チケットの受付状況は、イベントの開催日まで固定されている情報ではありません。受付中だったものが終了したり、一般発売が始まったり、受付条件が変わったりします。

例えば、さわやか五郎さんのBDイベントは、公式ページに掲載されている受付期間が2026年9月8日23:00までだったため、9月9日のスナップショットでは「販売終了」と記録しています。公式ページには、1部・2部の開場・開演時刻とゲストも掲載されています。

さわやか五郎さんのBDイベントを掲載しているのは、1部にモーニング娘。'26の井上春華さん・弓桁朱琴さんがゲスト出演する公式告知があるためです。2部のゲスト情報も詳細画面に残しています。対象アーティスト本人の単独公演だけでなく、追っているメンバーが出演する関連イベントも、予定を考える上で必要なものとして扱っています。

参照した公式ページ：[さわやか五郎バースデーイベント 二次募集＆ゲストのお知らせ](https://helloproject.com/event/4642a2c951474ab2cef37b25d209125ab56ce386cc6a6592c3745649e2522b8f/)

アプリでは、受付状況、受付期間、情報確認日、公式ページへのリンクを持たせています。これにより、「いつ確認した情報なのか」を画面上で分かるようにしました。

一方で、アプリの表示をチケット販売サイトの代わりにはしていません。申し込み前には、必ずリンク先の公式ページで最新の受付状況、対象公演、条件を確認してください。

この考え方で、前回以降に公式ページで確認できたOCHA NORMAの「クロフェス」、モーニング娘。'26の77thシングル発売記念イベント、宮本佳林が出演するラブライブ！関連イベントなども追加しました。前回の40件から、今回は58件まで増えています。

新しい予定を追加するときも、開催日・会場・イベント種別・公式URLを確認し、カレンダー上で意味が分かる短い表示名に整理しています。公式ページで確認できない出演時刻や終演時刻を推測して埋めることはしていません。「未発表」「時刻未確認」として残し、分からないものを分かったように見せない方針です。

## 6. 公開データの境界を決めた

FC向けイベントであっても、開催告知が一般公開されている場合があります。ただし、会員ページにログインして初めて見られる内容まで取得・掲載することはしません。

掲載対象は、確認時点で一般に閲覧できた公式ページの、イベント名・開催日・会場・開催地・出演者・受付状況の短い整理と公式URLです。

次のものは掲載しません。

- ログインが必要なページの本文
- FC会員限定ページの内容
- 会員番号などの個人情報
- 公式サイトの画像や長文本文
- SNS投稿だけを根拠にした予定
- 公開可否を判断できない情報

「公開されている事実だから、そのまま自由に転載できる」とは限りません。公式サイトの規約や権利条件を確認し、判断できないものは載せないようにしています。

## 7. Cloudflareで常時見られるようにした

前回はローカルで起動して確認するアプリでしたが、現在はCloudflare Workers Static Assetsにデプロイしています。

実際の構成はシンプルです。

```text
公式の公開ページ
        ↓ 確認・整理
src/data/events.ts
        ↓ npm test / npm run build
Cloudflare Workers Static Assets
        ↓
https://oshi-calendar.badterumaru.workers.dev/
```

イベントデータは静的なフロントエンドに同梱しています。データベースや有料APIを使っていないため、アプリを開くたびに別のサーバーで取得処理を走らせる構成ではありません。

「行きたい」の選択状態、出力履歴、自分用の終了予定は、利用中のブラウザのローカルストレージに保存します。サーバーに個人の選択内容を送信する機能はありません。

## 8. 日次更新は、アプリではなくCodex側のタスクで行う

現在は、毎日03:00（日本時間）に、Codexに登録したスレッドの定期タスクが、このローカルプロジェクトを対象に公式の公開ページを確認する運用を設定しています。GitHub ActionsやCloudflare Schedulerを常駐させているわけではありません。

処理の流れは次のとおりです。

1. 現在のイベントデータと公式ページを照合する
2. 新規イベントや受付状況の変更を確認する
3. 公式ページから明確に確認できた変更だけをデータへ反映する
4. テストとビルドを実行する
5. あらかじめ決めた確認条件を満たした場合だけCloudflareへデプロイする

ページ同士の内容が食い違う場合、会員限定情報しかない場合、公式URLを確認できない場合は、変更せずに報告するルールです。

つまり、アプリ自身が自動巡回しているわけではありません。Codexの実行環境がこのプロジェクトを確認し、条件を満たした場合だけ静的ファイルを公開し直す構成です。そのため、アプリを表示するCloudflare側に、別の常駐スケジューラを用意しているわけではありません。自動化の範囲を広げても、判断できない情報を無理に公開しないことを優先します。

## Codexに任せたこと、人が判断したこと

Codexには、次のような実装作業を依頼しました。

- React・TypeScript・Viteによる画面実装
- 月間カレンダーと月曜始まりへの変更
- 祝日表示とイベント種別フィルター
- スマートフォン向けの地名優先表示
- 「行きたい」の保存と公演単位の選択
- iCalendar出力と重複を減らす出力履歴
- イベントデータの構造化とテスト・ビルド
- Cloudflareへのデプロイ

一方で、次の内容は人が決めています。

- 対象にするアーティスト
- カレンダーで見たいイベントの範囲
- イベント名をどこまで短くするか
- 一般公開情報だけを扱う境界
- 公式ページを根拠にできるか
- 受付状況をどの表現で表示するか
- 不確実な情報を公開しない判断

AIはページの情報を整理したり、画面を作ったりするのは得意です。しかし、掲載してよい情報か、公式ページのどの記述を採用するか、現在も受付中と言ってよいかまで、無条件に任せられるわけではありません。

今回の改善では、AIに実装を任せながら、情報の境界と最終的な公開判断は人が持つ形にしました。

## まだ改善したいこと

現在のアプリは、公式公開ページを確認したスナップショットです。今後は、次の改善を検討しています。

- 公式ページの更新をより確実に検知する仕組み
- 同じイベントに複数の告知ページがある場合の整理
- 変更前後の差分を確認できる画面
- 情報源と確認日時を一覧で追える仕組み
- 外部カレンダーとの連携方法の改善

ただし、ページの自動取得やAIによる自動判断を増やすほど、表記ゆれ、誤認、公開範囲、サイト側の利用条件も考える必要があります。便利さだけを先に追わず、確認できる根拠を残せる範囲で広げていくつもりです。

## まとめ

最初は、3組の予定をひとつのカレンダーに並べるところから始めました。

そこから、地名を先に見る、イベント種別で絞る、公演単位で「行きたい」を選ぶ、時間付きで自分のカレンダーへ出力する、という形に改善しました。

同時に、チケット情報やFC向けイベントの扱いについても、公開範囲と確認日を意識するようになりました。

Codexを使うと、アイデアを画面にして試すところまでは速く進められます。ただ、何を正しい情報として載せるか、どこまで公開するかは、最後まで人が考える必要があります。

推し活の予定を眺めるだけでなく、「この現場に行きたい」と思ったときに次の行動へ移れるカレンダーを目指して、これからも少しずつ改善していきます。

次は、公式ページの更新前後の差分や、情報源と確認日時をさらに追いやすくする仕組みも試したいと思います。
